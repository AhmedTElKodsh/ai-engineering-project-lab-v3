# Codex learner-owned AI engineering workspace

This kernel is derived from the append-only planning memlog. The listed companions carry the complete teaching, curriculum and evidence contract; archived guides are provenance, not competing live instructions.

## Why

The learner needs practical AI engineering experience and defensible portfolio work for junior roles in Egypt and eligible remote markets. Moving the project-first medical/retail curriculum into a code-aware workspace creates an opportunity to connect instruction to actual work, while preventing agent-generated implementation from being mistaken for learner competence.

## Capabilities

- **CAP-1**
  - **intent:** The learner can resume the latest actual learning state across sessions.
  - **success:** A fresh lesson resumes the pending Q0 / 0.3 task without re-onboarding or assuming an application exists in this repository.
- **CAP-2**
  - **intent:** The learner can receive explanation, guided practice, assessment or explicitly requested implementation help with clear ownership.
  - **success:** Learn returns one meaningful action after instruction; Assess withholds the answer; Build together records help; maintainer requests run without student assessment.
- **CAP-3**
  - **intent:** The learner can build distinct medical-review and retail-support products through a practical initial route.
  - **success:** J0-J5 connects SDK/structured extraction, retrieval, SQL/tools/state and delivery to defined evidence; deeper testing, deployment and LLMOps remain later branches.
- **CAP-4**
  - **intent:** The learner and tutor can retain auditable evidence without inventing competence.
  - **success:** A successful run alone cannot complete 0.3; invalidated or contrary evidence cannot justify satisfied gates; native validation works without provider access or the author's Downloads folder.
- **CAP-5**
  - **intent:** Codex can discover and reuse project-specific tutoring guidance.
  - **success:** The tutor skill has valid metadata and resolving native references, routes ordinary lessons correctly, and excludes explicit maintainer work.
- **CAP-6**
  - **intent:** The maintainer can version and privately publish the configured workspace.
  - **success:** Private GitHub visibility and matching local/remote commit are verified after scoped checks; pre-existing curriculum and vendor skill sources are preserved.

## Constraints

- Current learner execution and understanding remain pending; actual app location and installed versions are unverified.
- Use synthetic medical notes and orders; never request/persist keys or patient data. Exact code semantics and source evidence survive host migration.
- Native policy and progress authorities are unique. Latest user direction and actual evidence supersede stale snapshots. Maintainer state is separate from learner competence.
- Initial application evidence is distinct from full curriculum completion, production readiness and vacancy eligibility. No timeline or employment guarantee.
- Preserve the V3.2 archive and vendor skill definitions; new project rules and the tutor skill supply customization.

## Non-goals

- Implementing either learner app during setup, running provider calls, publishing publicly, deploying clinical systems, executing real refunds/messages, or building a separate learning platform.
- Requiring enterprise infrastructure or every advanced framework before the first suitable application.

## Success signal

The configured private repository can be cloned and structurally validated, and a fresh tutoring interaction resumes the correct pending task while preserving student ownership. Static and simulated results are reported separately from real learner outcomes, which remain pending until observed.

- The authenticated personal account AhmedTElKodsh and available name `ai-engineering-project-lab-v3` are the initial private publication target.
- Python is available for maintainer validation; learner runtime/provider requirements are verified at lesson time.
