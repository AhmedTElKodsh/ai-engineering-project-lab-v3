# V3.2 Review and Revision Notes

**Revision date:** 2026-09-07

## Design decision

Prepare for junior applied AI work through two evolving products: medical document review and retail support/order assistance. Make initial applications a separate milestone from completing a broad curriculum or proving production readiness. This is a curriculum design choice informed by the user's objectives, primary project examples and a small vacancy sample, not a labor-market census.

## Preserved and intentionally not inferred

- Seven-source ownership, host-safe numeric indexing, decomposed first response access, current provider choice and Q0 / 0.3 resume point are retained.
- Core teaching content in 00, 04 and 06 is retained with targeted route and evidence corrections; 01, 02 and 05 are rewritten around the new path. 03 receives continuity updates without new learner achievements.
- The source status records prior onboarding as complete but the first run and understanding as pending. This revision does not interpret that as completed competence. The skill ledger remains Not started until qualifying evidence is recorded.
- Provider syntax is inherited from the baseline's dated reference claim, not newly runtime-verified. No environment/package versions are invented.
- No patient data, real customer data, credentials, uploads, provider calls, deployments, messages or learner code were involved.
- “Medical” means synthetic document processing and review. Clinical judgment and validation are outside the initial project's claims.

## Why retain deeper material?

The requested curriculum continues beyond the first job-application checkpoint. Existing playbook reference sections retain advanced practices for later learning. Their presence does not activate them. The quest map and early-route contract select the current scope; boundaries such as authorization still apply immediately when introduced.

The old Q1-Q4 milestone lists are replaced, not run alongside J1-J5. Q0's numbered milestones are preserved for live continuity. Q5-Q12 names remain in the later catalog; their capability families can be selected independently once prerequisites are met.

## Verification boundary

The accompanying validator checks source inventory and preservation hashes, local guide references, code-fence balance, route graph properties, selected cross-file gate invariants, Python syntax of the preserved first-call block, and equivalence to the inherited baseline code. It creates a live-source digest manifest. These are static checks, not proof that instructions will be followed by NotebookLM.

The guide revisions were inspected for sequencing and contradictory gates. No independent human learner pilot or actual NotebookLM trial was run for V3.2. The original V3.1.4.3 PASS report has not been reused as a V3.2 result. Learning effectiveness, completion-time estimates and hiring benefits remain hypotheses to test.

## Open decisions to resolve through evidence

Do not block the first lesson on these. Choose a local index/database when persistence is needed; choose an embedding route from actual cost/access constraints; use current model documentation at lesson time. Review eligible job requirements during J5 and earlier if the learner wants to apply. If repeated suitable roles require Docker/cloud or deeper ML, add a focused branch without expanding every early project into an enterprise system.
