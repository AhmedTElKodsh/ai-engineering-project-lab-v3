# Active increment assessment cards

Read only the active stage. [Progress protocol](PROGRESS_PROTOCOL.md) owns all gate/status rules; [teaching](TEACHING_GUIDE.md) owns delivery. These are acceptance contracts, not new progress IDs. Normal development requirements are visible; only the exact unfamiliar assessment probe/solution is withheld in Assess.

Record task/input, expected and observed behavior, safe evidence pointer, actual assistance and failure layer. Supported work is practice. Independent claims require unfamiliar work with none/docs assistance under the native protocol. A static fixture check does not establish model quality or learner understanding.

## J1 - Source-grounded support intake

Gates: execution, explanation, modification, debug. Use existing E05-E07 and continuing E04/E06 as genuinely demonstrated. Require explicit types/nullability/strictness, parse/schema/source distinctions, valid source ranges and semantic support. Unknown order stays null; not broken stays false. Preserve uncertainty and chronology.

Use [support fixtures](../fixtures/support/CASES.md) progressively: absence/negation/bad spans first, then remaining patterns before completion. Show source/value together and preserve corrections. Compare one change and a simple baseline, counting omissions. Probe with a new field or unsupported claim, not a retyped solution. A real quote can support the wrong value; diagnose that separately from a span mismatch.

## J2 - Required support-workflow transfer

Gates: modification, explanation, transfer. Keep E08/E09 IDs; the historical domain-transfer label now covers a meaningful different SupportOps constraint, not a required second medical app.

Adapt damaged-item intake to supplied customer/carrier statements that disagree. Retain attribution, missing information and conflict. Change a meaningful rule/input/language constraint, not names alone. No carrier API prerequisite. Separate Arabic/English results and disclose untested code-switching.

After supported practice, use a different case after the eligible delay. Follow the native ready contract if transfer is pending; do not claim retention from same-session copying or force idle waiting. Later tools can assess freshness and network failure on a new scenario.

## J3 - Policy finder and cited assistant

Gates: execution, explanation, modification, debug. E09-E13 as demonstrated. First show a finder with stable source/version/section IDs, a lexical baseline and one verified embedding route. Probe a chunk-boundary/ranking/version miss before generation.

Then require supported citations and defined absent/conflicting/superseded-evidence handling. Fixture checks catch nonexistent source IDs; source support still needs separate evaluation. Instruction-like documents cannot authorize actions. An unfamiliar bad answer must be traced to retrieval or generation evidence.

Compare framework responsibility only after the native path is understood. A justified no-adoption choice can show architectural judgment but not hands-on LangChain skill. Scope/language limits remain visible.

## J4 - Scoped tools and exact approval

Entry: J2 readiness for SQL/read tools. Completion also needs J3. Gates: execution, explanation, modification, debug; E14-E17 as demonstrated.

Verify expected SQL rows and trusted scope before model integration. Test allowed, denied, missing and database-error outcomes. Native tools validate args, preserve invocation identity, bound steps/time and never report exceptions as successful lookup.

Evaluate fictional BR01-BR08 with a fixed clock. The unchanged approved proposal has one defined local effect. Changed actor, target or parameters, expiry, stale policy/order, rejection, missing approval and replay produce zero additional effects. Probe a different-key request for the same scoped order line as well as same-key replay. Explain execution-time revalidation.

Never trade working approval semantics for a graph diagram. No real store writes. Local tests are not restart/concurrency/distributed proof. A selected later external-write adapter must reconcile unknown outcomes.

## Abstraction decision

For E13/E17, trace the native retrieval/state mechanism, identify what a proposed framework would own and what remains application-owned, compare costs, and state a concrete adoption trigger. A justified no-adoption decision remains acceptable under the native contract. If adopted, implement and debug one bounded slice; do not label a conceptual comparison hands-on competence or weaken safety invariants to fit a framework.

## J5 - Independent delivery

Gates: execution, explanation, modification, debug, transfer; E18-E22 plus route coverage. Show one reproducible application with locked dependencies, minimal validated API/interface, clear timeout/errors and appropriate bounded retry. Existing source/scope/action regression behavior must hold.

Freeze held-out expectations before use; report counts, denominator, config/date, critical failures, contamination, repeated-run variability and unknown metrics. Require unfamiliar modification, diagnosis, architecture/dataflow explanation and later transfer with normal docs allowed.

J5 explanation/modification/debug/transfer requires none/docs; execution may be supported. Ready requires E01-E22 at least practiced; completion also requires E22 independent or stronger and all initial route gates under the unchanged protocol. Do not infer operational or employment readiness.

When practical, observe another person attempting a normal task and record actual behavior and one correction or justified deferral. [Portfolio](PORTFOLIO.md) attaches interview-style Python/SQL/debug/architecture practice without another tracker or blocking course.
