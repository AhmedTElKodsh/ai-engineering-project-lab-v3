# Closed mini-projects inside J0-J5

This is the human-facing task map, not a parallel M/T/P progress tracker. Keep existing J stages and 0.3-0.9 identifiers. Each result is useful before its successor exists. Grow one codebase, not independent services.

## Closure contract

Define useful input/output, one dominant concept, starting behavior, smallest change, a normal/failure case and the actual run command once the path exists. Teach before asking a beginner to predict unfamiliar syntax. Expected output must not be labeled observed.

Close with a runnable artifact, focused checks, a learner-owned explanation/change, saved checkpoint and known limitation. Supported software completion and independent understanding are different. The [native protocol](../PROGRESS_PROTOCOL.md) owns readiness, delayed transfer and completion. Optional self-checks are not extra gates. No fixed duration or enterprise readiness is implied.

## J0: Reply draft from supplied evidence

Need: draft a response to one synthetic damaged-item message using a short policy excerpt. Result: ask which item was damaged without claiming order lookup or completed replacement.

Steps: reconcile the existing app and first-call example; explain the SDK/network/model boundary; run one authorized call; inspect content and available usage; predict/change one input; then introduce tiny structured facts and a local malformed payload using the existing 0.3-0.9 ladder. Preserve working setup instead of creating a service scaffold.

Variation: remove a necessary detail and explain what changes and remains unverified. Stop: one small program runs and is understood. No API server, database, retrieval, graph, CI or embedding provider is required. Interview prompt: where does the SDK run, and which output claims can you verify?

## J1: Intake with source evidence

Need: free text is hard to review. Result: stated order reference, damage report, missing information and evidence beside the original message.

Steps: one field -> missing/null -> explicit negation -> quote/span -> multiple claims -> human correction. Use [seven fixture patterns and eight bad-output examples](../../fixtures/support/CASES.md) progressively. Write basic tests beside the first deterministic function; avoid a testing-framework architecture.

Variation: add a field or diagnose a new chronology/source failure. Stop: useful intake runs without an order database. Interview prompt: how can valid JSON, valid schema and a resolving quote still contain a false claim?

## J2: Required delivery-dispute transfer

Need: damaged-item rules do not automatically handle conflicting sources. Result: separate customer nonreceipt and supplied carrier-delivered claims, with attribution and conflict flag.

Steps: sketch changed schema -> retain both claims -> handle absent carrier evidence -> later unfamiliar rule/language variation. Use supplied text, not a new carrier service. Stop: run both scenarios and explain what transferred and what changed. Retain required delayed transfer; do not substitute renaming for understanding.

## J3: Two separate wins

Policy finder: three short versioned policy files, labeled questions, ranked evidence and lexical baseline, then one documented embedding route and visible similarity. Diagnose a retrieval miss. This search-only tool is already a finished mini-project.

Cited assistant: reuse the finder, add supported answers and insufficient/conflicting-evidence behavior. Test instruction-like source text. Inspect context before changing the generation prompt. Stop: show a cited answer, abstention and diagnosed miss. Interview prompt: which observation distinguishes retrieval failure from generation failure?

## J4: Three separate wins

Scoped lookup: parameterized SQL on synthetic rows; directly test allowed/denied/nonexistent/service-error outcomes before a model requests it.

Order investigation: a typed native read-tool boundary, matching call/result identity, bounded loop and honest errors. Combine policy evidence only after J3 readiness. Prove that a tool exception does not become a success claim.

Approved simulation: apply BR01-BR08, show the immutable proposal, approve/reject the exact binding, execute one local effect and test altered/stale/replayed requests. No real store writes. Stop: one successful approved simulation and denied paths with zero additional effects. Interview prompt: why is safe retry more than a reassuring model response?

## J5: One reproducible release

Wrap working functions with a small API/interface and actual setup/run instructions. Freeze held-out expectations before evaluation, disclose contamination and synthetic scope, and report unknown metrics as unknown. Independently explain, change and debug; later transfer a boundary to a different support constraint with normal docs allowed. Observe another person trying a task when practical.

Include a project explanation, small Python/SQL exercise and architecture tradeoff. Expand interview practice from observed gaps, not a new mandatory course. Stop: another person can reproduce the release and the learner can defend its boundaries.

## Selected extensions

Follow [named deferral triggers](../CURRICULUM.md): persistent knowledge/indexes, hybrid/reranking, durable LangGraph recovery, classical ticket classification, hosted traces, auth/deployment/queues/CI, MCP or multimodal intake. Give each selected extension its own bounded input/output and checks. None silently becomes an earlier mini-tool prerequisite.
