## J1 - Support-case intake with evidence and review

Build from one field to case ID, stated order reference, reported damage, missing information, source evidence and review flags. A customer report is not independently verified business data. Unknown is null, explicit negation is false; preserve uncertainty and chronology.

Use [support fixtures](../fixtures/support/CASES.md). Separate parsing, schema validity, span resolution and semantic support. Source spans use original Python-string code-point indices. A real quote may not support the attached value. Show original message and extracted fields together, preserving correction history.

Begin with absence, negation and mismatched spans; add uncertainty, chronology and instruction-like content before completion. Introduce a few deterministic tests beside a local function; pytest does not require a large fixture architecture or CI. Evaluate Arabic and English separately. Compare one schema/prompt change with a simple baseline on fixed examples; reserve an unfamiliar case before tuning.

Close the intake tool with a successful result, correct omission/negation handling, and one diagnosed failure. Require learner explanation, modification and debugging under the native gates. Interview practice: explain how a schema-valid claim can still be unsupported. No order database or second product is required.

## J3 - Retail policy RAG: finder before generation

First close a policy-finder mini-project using a small versioned corpus, visible chunks and labeled relevant sources. Three short policies are sufficient to start. Compare a lexical baseline with one verified embedding route and inspectable similarity. [DR-001](DECISIONS.md) is unverified and cannot establish a working Groq embedding endpoint. Do not install multiple retrieval frameworks.

Then add cited answers, insufficient-evidence handling, and missing/conflicting/superseded/instruction-like documents. Measure retrieval Recall@k separately from supported answers, citation correctness and abstention. Apply access scope before retrieval whenever protected content exists. Verify language suitability rather than inferring Arabic quality from UI translation.

Inspect query, eligible documents, ranking, chosen context and generated claims locally. A tracing product becomes useful when nested runs are hard to follow and external transmission is authorized. Compare a bounded LangChain slice after understanding the native mechanism. A justified no-adoption choice remains architectural evidence, not hands-on framework competence.

Close with a finder demo, cited answer, abstention and diagnosed retrieval miss. Do not hide a ranking/version bug by rewriting the answer prompt.

## J4 - Retail order tools and state

Close three results separately: direct scoped SQL lookup, a native read-tool loop, and an approved simulated replacement. Use SQLite unless a suitable existing database is available. Write parameterized SELECT/WHERE/JOIN/aggregation and expected rows before model integration.

Trusted caller scope controls fixed tools; a model-supplied customer/tenant/role does not grant permission. Match tool-result identity to the invocation, bound steps/time, and preserve service-failure versus confirmed absence. Combine order and policy evidence only when both branches are ready.

Use [BR01-BR08](project/CONTRACTS.md) for the fictional action. The model proposes; code evaluates eligibility. Bind approval to immutable identity/version or digest, trusted actor, target and exact arguments. Recheck permission, freshness, expiry, stock, duplicates and binding immediately before the effect. Consume approval once with the defined local effect and preserve its result. Mutation, rejection, missing/stale approval, substitution and replay produce zero additional effects.

Test with fake tools before model integration. Never turn a timeout into success or blindly retry an unknown consequential write. LangGraph is conditional on actual branching/checkpoint/recovery needs. Local sequential correctness does not prove restart durability or concurrent/distributed guarantees; those require selected Q6/Q11 evidence. No real refunds, shipping, replacements or messages.

## J5 - Delivery pass and initial application checkpoint

Pass 1: one product, reproducible by another person. Add a small validated API/interface over working functions, locked dependencies, clear failures and suitable bounded retries. Consolidate deterministic tests separately from model evaluations. A local demo is sufficient; deployment is selected depth.

Pass 2: extend early unfamiliar probes into a held-out set with frozen expectations. The earlier 20-30 case heuristic now concerns one product when scope/budget justify it, not statistical sufficiency. Report counts, denominators, failure categories, model/config/date, contamination, language scope and available usage/latency. Repeat a subset for variability. Unknown is not zero.

Pass 3: independently explain, modify, debug and later transfer a boundary to another support constraint. Ordinary docs are allowed. J5 ownership gates remain none/docs; execution can be supported. E01-E22 practiced coverage is required for readiness; full completion also requires E22 independent or stronger and all route gates under the unchanged protocol. Observe one other person attempting a normal task when practical and record actual usability evidence.

Use [portfolio](PORTFOLIO.md) for project-linked interview practice and honest handoff. Applying to a suitable role is not gated on every later module.
